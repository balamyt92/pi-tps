# pi-tps

Честная статистика генерации LLM для [pi](https://github.com/badlogic/pi-mono): скорость генерации, задержка первого токена, диагностика спекулятивного декодирования.

## Установка

### Из git-репозитория

```bash
pi install git:github.com/<user>/pi-tps@v1.1.0
```

Поддерживаются HTTPS и SSH:

```bash
pi install https://github.com/<user>/pi-tps@v1.1.0
pi install git:git@github.com:<user>/pi-tps@v1.1.0
```

### Из локальной папки (для разработки)

```bash
pi install /path/to/pi-tps
```

После установки — `/reload` в сессии или перезапуск pi.

## Что показывает

### Уведомление после каждого хода агента

```
⚡ 77.8 ток/с · 1-й токен 1.27s · 350 ток. (текст 330) · контекст 1,200 · ход 8.1s · 2 выз.
```

- **⚡ скорость (eff tok/s)** — главная метрика: output / (отправка запроса → последний токен). Совпадает с реальным временем ожидания ответа (проверено против логов llama.cpp с точностью <5%).
- **1-й токен (TTFT)** — время до первого сгенерированного токена.
- **ток. / текст** — сгенерированные токены; отдельно текстовая часть (без reasoning).
- **контекст** — размер входного контекста последнего отчитавшегося вызова.
- Сбойные и незавершённые вызовы помечаются в конце строки: `❌ 1 сбой · ⚠️ 1 вызов не завершён`.

### Команда `/tps`

Карточка на каждый LLM-вызов + итоги:

```
✅ toolUse  #1 — 100 ток. out (reasoning 20) · in 1,000
   скорость 45.5 ток/с · decode 200.0 ток/с · 1-й токен 1.70s
   60 симв. (+thinking 19) · 12 дельт · ~8.33 ток/дельта · паузы p50 40ms / p95 100ms

✅ stop  #2 — 250 ток. out · in 1,200
   скорость 108.7 ток/с · decode 170.1 ток/с · 1-й токен 0.83s
   340 симв. · 50 дельт · ~5.00 ток/дельта · паузы p50 30ms / p95 30ms

── ИТОГИ · 2 успешных вызова ──
⚡ Скорость:    77.78 ток/с  — твоя реальная: запрос → последний токен
⏱  1-й токен:   1.27s avg · 1.70s max
🔤 Токены:      350 out = текст 330 + reasoning 20
🗒  Контекст:    max 1,200 · cache read 1,100
💬 Символы:     400 текст · 203.0 зн/с
🔮 ~5.65 ток/дельта — похоже на speculative decoding (MTP)

Скорость (eff) = запрос → последний токен; совпадает с wall сервера (<5%).
Decode = 1-й → последний токен; завышен буфером 1-й дельты — только для диагностики.
```

- **скорость (eff)** — надёжная метрика: запрос → последний токен.
- **decode** — «чистое» окно генерации (первый → последний токен); оставлено для диагностики: на коротких ответах систематически завышено из-за буфера первой дельты.
- **паузы p50/p95** — распределение интервалов между дельтами. Сильный перекос p95 → берсты доставки.
- **~ток/дельта** — при >1.5 экстеншн помечает вероятное спекулятивное декодирование (MTP и т.п.).
- **Статусы вызовов**: `✅` — успешный, `❌ error/aborted` — сбойный, `⚠️ не завершён` — стрим оборвался до финализации. Сбойные и незавершённые исключены из итогов, но видны в карточках.

## Семантика событий (почему цифры честные)

Проверено по исходникам pi (agent-loop.js / agent-session.js):

- `agent_start`/`agent_end` эмитятся на **каждый** low-level run: ретраи, авто-компакция и continuation'ы перевзводят эту пару. Поэтому pi-tps сбрасывает данные только когда предыдущий ход уже устаканился — **ретрай посреди хода не стирает статистику**.
- Итоговое уведомление привязано к `agent_settled` — он эмитится один раз за ход пользователя, когда pi гарантированно не продолжит работать автоматически.
- Каждая попытка запроса — отдельный provider request: проваленная попытка становится отдельной `❌`-записью и не портит eff TPS успешных вызовов.
- Окно eff закрывается на **последнем токене**, а не на финализации сообщения: post-stream оверхед не занижает метрику.
- Время в знаменатель итоговых TPS берётся только у вызовов с токенами: вызов без usage не раздувает знаменатель.

## Особенности для локального инференса

Клиентский `usage` от локальных серверов (llama.cpp, llama-swap и др.) может расходиться с их внутренними счётчиками, а prompt-caching на стороне сервера не отражается в клиентских полях `cacheRead`. Экстеншн честно сообщает об этом и опирается только на измеримые клиентские тайминги.
